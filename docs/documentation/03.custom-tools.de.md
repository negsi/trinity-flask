## 1. Architektur & Lifecycle von Werkzeugen

Ein Werkzeug in Trinity ist eine zustandslose oder zustandsbehaftete Python-Funktion, die über den `ToolRegistry`-Service aufgerufen wird:

```
┌────────────────────────────────────────────────────────┐
│               LLM generiert Task Chain                 │
│         { "tool": "custom_tool", "parameters": {...} } │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│            AgentOrchestrator / TaskEngine              │
│       • Löst Tokens auf ([STEP_1], REF:PAYLOAD_*)      │
│       • Injiziert Session-Metadaten (conversation_id)  │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│                     ToolRegistry                       │
│       • Prüft Verfügbarkeit des Callables              │
│       • Reicht Storage-, Mail- oder DB-Services durch   │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│                 Eigene Tool-Funktion                   │
│           def custom_tool(*args, **kwargs)             │
└────────────────────────────────────────────────────────┘
```

Jedes Werkzeug profitiert automatisch von:
- **Sandbox-Isolation:** Lese- und Schreiboperationen werden standardmäßig auf das Konversationsverzeichnis beschränkt (`instance/conversations/<conversation_id>/`).
- **Token-Auflösung:** Platzhalter aus vorherigen Schritten (wie `[STEP_1]`) werden vor dem Aufruf der Funktion automatisch durch das Ergebnis des jeweiligen Schritts ersetzt.
- **Inhalts-Payloads:** Große Textmengen oder Skripte, die via `REF:PAYLOAD_STEP_N` ausgelagert wurden, treffen unmaskiert im Parameter ein.

## 2. Anatomie einer Tool-Funktion

### Signatur & Sandboxing

Eine saubere Tool-Funktion sollte mindestens folgende Konventionen einhalten:
- Verwende **strikte Typisierung** (Type Hints) nach Python 3.10+.
- Fange optionale Framework-Metadaten über `**kwargs` ab (`conversation_id`, `base_dir`, etc.).
- Pfade dürfen **niemals unvalidiert** aus Benutzer-Eingaben übernommen werden.

```python
from pathlib import Path
from typing import Any
import logging

logger = logging.getLogger(__name__)

def my_custom_tool(
    param_a: str,
    param_b: int = 10,
    conversation_id: str | None = None,
    base_dir: str | Path | None = None,
    **kwargs: Any,
) -> dict[str, Any] | str:
    """Kurze Beschreibung für Logging und Introspektion."""
    try:
        # Eigentliche Logik hier...
        return {"status": "success", "result": f"Verarbeitet: {param_a}"}
    except Exception as exc:
        logger.error(f"Fehler bei Ausführung von my_custom_tool: {exc}", exc_info=True)
        return {"error": str(exc)}
```

### Rückgabewerte & Fehlerbehandlung

- **Rückgabetyp:** Gib strukturierte Dictionaries (`dict[str, Any]`) oder saubere Plaintext-Strings zurück.
- **Keine unbehandelten Exceptions:** Werkzeuge sollten deterministisch `{"error": "Fehlermeldung"}` oder eine verständliche Fehlerbeschreibung als String zurückliefern, damit der Agent in einer Task Chain darauf reagieren und korrigierende Schritte einleiten kann.

## 3. Schritt-für-Schritt-Anleitung: Tool-Registrierung

### Schritt 1: Python-Modul erstellen

Lege deine Werkzeuge im Verzeichnis `app/services/tools/` ab. Erstelle beispielsweise die Datei `app/services/tools/custom_network_tools.py`:

```python
# app/services/tools/custom_network_tools.py
import socket
from typing import Any

def dns_lookup(hostname: str, **kwargs: Any) -> dict[str, Any]:
    """Löst einen Hostnamen in dessen IPv4-Adressen auf."""
    try:
        clean_host = hostname.strip().replace("http://", "").replace("https://", "").split("/")[0]
        _, _, ip_addresses = socket.gethostbyname_ex(clean_host)
        return {
            "hostname": clean_host,
            "ip_addresses": ip_addresses
        }
    except socket.gaierror as err:
        return {"error": f"DNS-Auflösung fehlgeschlagen: {err}"}
```

### Schritt 2: Registrierung in der ToolRegistry

Öffne `app/services/tools/registry.py` und binde deine neue Funktion ein.

#### Variante A: Fest in `get_tools()` hinterlegen (Standard für Kern-Tools)

```python
# app/services/tools/registry.py
from app.services.tools.custom_network_tools import dns_lookup

class ToolRegistry:
    # ...
    def get_tools(self) -> dict[str, Callable[..., Any]]:
        base_tools: dict[str, Callable[..., Any]] = {
            "fetch_url": fetch_url,
            "web_search": web_search,
            "message_llm": message_llm,
            "message_agent": self.message_agent,
            "call_api": call_api,
            "write_file": self.write_file,
            "read_file": self.read_file,
            "send_email": self.send_email,
            "generate_image": self.generate_image,
            "manage_odf": self.manage_odf,
            # Neues Custom Tool:
            "dns_lookup": dns_lookup,
        }
        base_tools.update(self._custom_tools)
        return base_tools
```

#### Variante B: Dynamisch zur Laufzeit registrieren

Falls du ein Plugin-System nutzt oder Werkzeuge modular zuschaltest:

```python
tool_registry.register_tool("dns_lookup", dns_lookup)
```

### Schritt 3: Dependency Injection im Container anpassen

Wenn dein Werkzeug Zugriff auf Infrastruktur-Services benötigt (z. B. `FileStorageService` oder `DatabaseSession`), erstelle eine Wrapper-Methode auf der `ToolRegistry` und injiziere die Abhängigkeit über `app/containers.py`:

```python
# app/services/tools/registry.py
class ToolRegistry:
    def __init__(
        self,
        file_storage_service: FileStorageService,
        email_service: EmailService | None = None,
        # Weitere Abhängigkeiten ...
    ) -> None:
        self.file_storage_service = file_storage_service
        # ...
```

### Schritt 4: Werkzeug im System-Prompt hinterlegen

Damit das LLM weiß, **dass** das Werkzeug existiert und **wie** es aufgerufen werden muss, trage es im Basis-Prompt (`app/templates/prompts/base_agent.prompt.md`) oder im individuellen `system_prompt` des Agenten ein:

```markdown
11. `dns_lookup`: Führt eine DNS-Namensauflösung für eine Domain durch.
    - **Parameter:** `hostname` (string, Pflicht: Domain oder Hostname ohne Protokoll).
    - **Beispiel:** `{"hostname": "example.org"}`
```

## 4. Praxisbeispiele

### Beispiel 1: DNS- & Domain-Lookup-Tool (`dns_lookup`)

Ermöglicht Sicherheits- und Netzwerkagenten das Abfragen von DNS-Einträgen.

```python
# app/services/tools/network_tools.py
import socket
from typing import Any

def dns_lookup(hostname: str, **kwargs: Any) -> dict[str, Any]:
    """
    Führt einen Forward-DNS-Lookup durch.

    Args:
        hostname: Domainname (z. B. 'github.com')
    """
    if not hostname:
        return {"error": "Parameter 'hostname' darf nicht leer sein."}

    # Bereinigung: Protokoll-Präfixe und Pfade entfernen
    domain = hostname.strip().lower()
    for prefix in ["https://", "http://"]:
        if domain.startswith(prefix):
            domain = domain[len(prefix):]
    domain = domain.split("/")[0].split(":")[0]

    try:
        primary_name, aliases, ip_list = socket.gethostbyname_ex(domain)
        return {
            "query": hostname,
            "canonical_name": primary_name,
            "aliases": aliases,
            "ip_addresses": ip_list,
            "status": "success",
        }
    except socket.gaierror as e:
        return {
            "query": hostname,
            "status": "failed",
            "error": f"DNS Lookup fehlgeschlagen: {e.strerror} (Code: {e.errno})"
        }
```

### Beispiel 2: Python Code-Linter & AST-Prüfer (`lint_python_code`)

Prüft Python-Dateien oder Code-Snippets im Konversationsverzeichnis auf Syntaxfehler, bevor sie ausgeführt oder committed werden.

```python
# app/services/tools/dev_tools.py
import ast
from pathlib import Path
from typing import Any

def lint_python_code(
    file_path: str | None = None,
    code: str | None = None,
    conversation_id: str | None = None,
    base_dir: str | Path | None = None,
    **kwargs: Any,
) -> dict[str, Any]:
    """
    Validiert Python-Quellcode auf Syntaxfehler via AST-Parsing.

    Args:
        file_path: Relativer Pfad zur Datei im Workspace (optional).
        code: Direkter Code-String zur Prüfung (optional).
    """
    target_code = code

    # Falls file_path angegeben, lese den Inhalt aus dem sicheren Workspace
    if file_path:
        if not base_dir or not conversation_id:
            return {"error": "Workspace-Kontext (base_dir, conversation_id) fehlt."}

        safe_path = Path(base_dir) / conversation_id / Path(file_path).name
        if not safe_path.is_file():
            return {"error": f"Datei '{file_path}' wurde im Workspace nicht gefunden."}

        try:
            target_code = safe_path.read_text(encoding="utf-8")
        except Exception as err:
            return {"error": f"Fehler beim Lesen der Datei: {err}"}

    if not target_code:
        return {"error": "Weder 'code' noch 'file_path' wurde übergeben."}

    try:
        tree = ast.parse(target_code)
        
        # Einfache AST-Statistiken extrahieren
        function_count = sum(isinstance(node, ast.FunctionDef) for node in ast.walk(tree))
        class_count = sum(isinstance(node, ast.ClassDef) for node in ast.walk(tree))

        return {
            "valid": True,
            "message": "Syntax ist einwandfrei.",
            "metrics": {
                "functions": function_count,
                "classes": class_count,
                "lines": len(target_code.splitlines())
            }
        }
    except SyntaxError as syntax_err:
        return {
            "valid": False,
            "error": "SyntaxError",
            "message": syntax_err.msg,
            "line": syntax_err.lineno,
            "offset": syntax_err.offset,
            "text": syntax_err.text.strip() if syntax_err.text else None,
        }
```

### Beispiel 3: SQLite Query- & Tabellen-Inspektor (`query_sqlite`)

Erlaubt Data-Science-Agenten das schreibgeschützte Abfragen lokaler SQLite-Datenbanken innerhalb des Workspaces.

```python
# app/services/tools/db_tools.py
import sqlite3
from pathlib import Path
from typing import Any

def query_sqlite(
    db_filename: str,
    sql_query: str,
    max_rows: int = 50,
    conversation_id: str | None = None,
    base_dir: str | Path | None = None,
    **kwargs: Any,
) -> dict[str, Any]:
    """
    Führt schreibgeschützte SELECT-Queries auf einer Workspace-SQLite-DB aus.

    Args:
        db_filename: Name der SQLite-Datei (z. B. 'data.db').
        sql_query: Das auszuführende SELECT-Statement.
        max_rows: Maximale Ergebniszeilen (Standard: 50).
    """
    if not sql_query.strip().lower().startswith("select"):
        return {"error": "Sicherheitsbeschränkung: Nur 'SELECT'-Abfragen sind gestattet."}

    if not base_dir or not conversation_id:
        return {"error": "Workspace-Kontext fehlt."}

    # Sandbox-Pfad absichern
    db_path = (Path(base_dir) / conversation_id / Path(db_filename).name).resolve()
    if not db_path.is_file():
        return {"error": f"Datenbankdatei '{db_filename}' existiert nicht im Workspace."}

    try:
        # Im Read-Only-URI-Modus öffnen
        uri = f"file:{db_path.as_posix()}?mode=ro"
        with sqlite3.connect(uri, uri=True, timeout=5.0) as conn:
            conn.row_factory = sqlite3.Row
            cursor = conn.cursor()
            cursor.execute(sql_query)
            
            columns = [col[0] for col in cursor.description] if cursor.description else []
            rows = [dict(row) for row in cursor.fetchmany(max_rows)]

            return {
                "status": "success",
                "row_count": len(rows),
                "columns": columns,
                "data": rows,
                "truncated": len(rows) == max_rows
            }
    except sqlite3.Error as db_err:
        return {"status": "error", "error": f"SQLite-Fehler: {db_err}"}
```

## 5. Best Practices & Sicherheitsrichtlinien

1. **Pfad-Traversal verhindern:**
   Nutze niemals ungeprüfte relative Pfade wie `../../etc/passwd`. Nimm stets `Path(filename).name`, um Verzeichniswechsel zu unterbinden, oder validiere, dass der aufgelöste Zielpfad (`.resolve()`) strikt innerhalb von `Path(base_dir) / conversation_id` liegt.

2. **Keine Destruktiven Befehle ohne Absicherung:**
   Operationen wie `eval()`, `exec()` oder Shell-Subprozesse (`subprocess.run(..., shell=True)`) sollten vermieden werden. Falls Code ausgeführt werden muss, nutze AST-Checks oder dedizierte Container/Sandboxes.

3. **Timeouts setzen:**
   Netzwerkaufrufe (`requests`, `socket`, APIs) und Datenbankzugriffe müssen immer mit einem expliziten `timeout` versehen werden (z. B. `timeout=10`), damit blockierte Sockets nicht den Worker-Thread des Flask-Backends lahmlegen.

4. **Kompakte Ausgaben für das LLM:**
   Agenten verarbeiten Werkzeug-Rückgaben im nächsten Schritt über `message_llm`. Riesige Datenstrukturen (z. B. 10.000 Tabellenzeilen) sprengen das Token-Fenster. Limitiere Listen immer über Parameter wie `max_results` oder `max_rows`.
