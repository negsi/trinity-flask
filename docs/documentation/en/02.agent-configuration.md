This guide describes the configuration parameters, the interaction with the system prompt, and the orchestration of autonomous task chains.

## 1. Anatomy of a Trinity Agent

An agent in Trinity consists of four pillars:

```
┌────────────────────────────────────────────────────────────────────────┐
│                             TRINITY AGENT                              │
├───────────────────────┬───────────────────────┬────────────────────────┤
│ 1. Identity & Prompt  │ 2. Memory & Context   │ 3. Knowledge Base      │
│   • Name              │   • memory_enabled    │   • Attached Files     │
│   • Description       │   • memory_mode       │   • Inline Content     │
│   • System Prompt     │   • memory_limit_type │   • Workspace Files    │
│                       │   • message_count     │                        │
├───────────────────────┴───────────────────────┴────────────────────────┤
│ 4. Tool Execution Runtime                                              │
│   • Task Chain Planner (JSON Task Engine)                              │
│   • Local Tools (Filesystem, Web, ODF, Email, APIs)                    │
│   • Delegation Interface (Sub-Agent Calls)                             │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Configuration Parameters & Data Model

The `Agent` domain entity in the Flask backend (`app/domain/models/agent.py`) defines all attributes:

| Parameter | Data Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `name` | `string` | *(Required)* | Unique, concise designation (1 to 100 characters). |
| `description` | `string` | `None` | Short description of the deployment area (max. 500 characters). |
| `system_prompt` | `string` | `None` | Custom instruction for role, tone, and tool behavior. |
| `memory_enabled` | `boolean` | `false` | Completely activates or deactivates conversation memory. |
| `memory_mode` | `enum` | `"user_only"` | Filters the history: `"user_only"` (user prompts only) or `"all"` (incl. assistant responses). |
| `memory_limit_type` | `enum` | `"all"` | Type of limitation: `"all"` (unlimited) or `"message_count"` (last $N$ messages). |
| `memory_message_count`| `integer` | `None` | Limit when using `"message_count"`. Must be $> 0$ if active. |
| `datasources` | `list` | `[]` | List of linked knowledge base documents (`Datasource`). |

## 3. Context Control & Agent Memory

Trinity uses a multi-tier storage system. The LLM receives a structured view of past history with every request.

### Memory Topologies Compared

```
Mode: "user_only"                              Mode: "all"
┌────────────────────────┐                    ┌────────────────────────┐
│ User: How to create... │                    │ User: How to create... │
├────────────────────────┤                    ├────────────────────────┤
│ [Assistant skipped]    │                    │ Assistant: Here is ... │
├────────────────────────┤                    ├────────────────────────┤
│ User: Add step 2       │                    │ User: Add step 2       │
└────────────────────────┘                    └────────────────────────┘
-> Saves ~50-70% tokens                       -> Full dialogue context
-> Ideal for task-oriented agents             -> Ideal for coaching, roleplay
```

### Choosing the Appropriate Strategy

1. **Pure Task and Interface Agents (Web Scraping, Git Bots, Code Generators):**
   - `memory_enabled`: `true`
   - `memory_mode`: `"user_only"`
   - `memory_limit_type`: `"message_count"`
   - `memory_message_count`: `6` to `10`
   - *Advantage:* Minimizes token costs and prevents extensive code outputs from past steps from clogging the context window.

2. **Reflective & Iterative Agents (Proofreading, Document Creation, Support):**
   - `memory_enabled`: `true`
   - `memory_mode`: `"all"`
   - `memory_limit_type`: `"message_count"`
   - `memory_message_count`: `14` to `20`
   - *Advantage:* The agent remembers its own intermediate drafts and phrasing suggestions.

3. **Stateless Pipelines (Microservice Workers):**
   - `memory_enabled`: `false`
   - *Advantage:* Each request is fully isolated. No drift from previous conversations.

## 4. Prompt Architecture & System Prompt Design

### The Two-Tier Structure (Base Prompt vs. Custom Prompt)

Trinity automatically prefixes every user-specific system prompt with the system-wide base prompt (`base_agent.prompt.md`). This anchors immutable core rules:
- Definition of available tools and their schemas
- Directory structure and paths of the current session
- JSON formatting rules for task chains
- Offloading of payloads via content payloads (`REF:PAYLOAD_STEP_N`)

The agent's individual `system_prompt` complements this base prompt with role, expertise, and instructions.

### Structure of a Productive System Prompt

A robust system prompt should be divided into four sections:

1. **Role & Mission:** Who is the agent? What is its primary value proposition?
2. **Workflow & Heuristics:** What steps does it take by default? When does it access which tools?
3. **Formatting & Output Guidelines:** How does it structure intermediate steps and final results?
4. **Limits & Negative Examples:** What is the agent explicitly prohibited from doing?

### Tool Conditioning & Task Chain Control

To prevent misplanning by the internal task engine, the system prompt should specify concrete behavioral patterns for tools:

- **Single-Stage vs. Multi-Stage Plans:** For unknown target links, the agent must first plan a 1-phase fetch (`is_complete: false`) to inspect links before loading detail pages.
- **No Blind URLs:** The agent must not invent URLs. Searches must be initiated via `web_search`.
- **Payload Usage:** Source code, templates, and long markdown texts must strictly be offloaded via the content payload block to prevent faulty JSON escapes.
- **ODF Documents:** For `.ods` spreadsheets, explicit reference must be made to English formula names (`=SUM()`, `=AVERAGE()`).

## 5. Working with Knowledge Bases & Datasources

Documents uploaded via the API endpoint `/api/v1/agents/<agent_id>/datasources` end up in the agent's knowledge base:

- Document contents are embedded into the system context under the marker `### KNOWLEDGE_BASE:` when a chat starts.
- **Important for the System Prompt:** The agent should be informed that knowledge base contents are already present in the prompt and that **no** `read_file` should be executed for them. The `read_file` tool is exclusively intended for files generated in the conversation folder during the session.

## 6. Sub-Agent Orchestration

Trinity allows agents to delegate tasks to colleagues.

```
┌─────────────────────────┐
│     Lead Agent          │
│ (e.g. IT Project Mgr)   │
└────────────┬────────────┘
             │  tool: "message_agent"
             │  target_agent_id: "6d08b3a3-..."
             ▼
┌─────────────────────────┐
│     Sub-Agent           │
│ (Frontend Architect)    │
└─────────────────────────┘
```

**Rules for Multi-Agent Prompts:**
- References to sub-agents must use the exact UUID from the configuration list.
- The result of a sub-agent is final (`is_complete: true`). No downstream re-evaluation by another `message_llm` is required unless multiple reports are being synthesized.
- Circular references are intercepted by Trinity at a nesting depth of $3$.

## 7. Complete Reference Configurations

### Scenario A: Research Assistant & Fact Checker

An agent for sound internet research that checks sources, draws cross-references, and creates structured dossiers.

#### Configuration Payload (REST API)
```json
{
  "name": "Fact Finder & Analyst",
  "description": "Performs structured web research and creates source-based dossiers.",
  "memory_enabled": true,
  "memory_mode": "user_only",
  "memory_limit_type": "message_count",
  "memory_message_count": 8,
  "system_prompt": "You are a precise fact-checking and research analyst.\n\n### WORKFLOW:\n1. When information is needed, first perform a targeted search using 'web_search'.\n2. Select the 2-3 most relevant source URLs and read the full text via separate 'fetch_url' steps (no summaries from teasers!).\n3. Process the extracted texts via 'message_llm' into a coherent dossier.\n4. Save the result structurally via 'write_file' as a markdown file under 'reports/analysereport.md'.\n\n### RULES:\n- No fabricated facts or URLs.\n- Cite the primary source with date for every key statement.\n- Keep answers factual, neutral, and structured in tables."
}
```

An agent for creating release notes and changelogs based on git patches and commits.

#### Configuration Payload (REST API)
```json
{
  "name": "Git Release Manager",
  "description": "Creates structured CHANGELOGs and release notes from patches and diffs.",
  "memory_enabled": true,
  "memory_mode": "user_only",
  "memory_limit_type": "message_count",
  "memory_message_count": 4,
  "system_prompt": "You are a highly precise release and changelog manager for software projects.\n\n### FORMATTING GUIDELINES:\nPopulate changelogs strictly according to the following standard:\n\n# [Unreleased]\n\n### Added\n- Feature 1\n- Feature 2\n\n### Changed\n- Change 1\n\n### Fixed\n- Bugfix 1\n\n### RULES:\n- Use exclusively British or American English.\n- Use '-' as bullet points.\n- Separate the first item of each category from the heading with a blank line.\n- Enclose code snippets in backticks.\n- Always secure files in the workspace via 'write_file'."
}
```

## 8. Pre-Deployment Checklist

Before an agent is deployed to production, the following points should be checked:

- [ ] **Name & Description:** Are role and task area clearly demarcated?
- [ ] **Token Economy:** Is `memory_mode: "user_only"` active if the agent primarily generates code or long files?
- [ ] **Task Chain Suitability:** Does the prompt explicitly demand intermediate steps via `message_llm` for data processing?
- [ ] **Tool Discipline:** Has the agent been prohibited from hallucinating URLs or facts?
- [ ] **Formula Compatibility:** Are ODF formulas conditioned to English designations?
- [ ] **Knowledge Base:** Are all required reference documents attached and unnecessary legacy data removed?
