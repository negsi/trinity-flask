# Trinity Agent Designer: Enterprise Cloud- & API-Agenten

> **10 Referenzbeispiele für Google Cloud, Azure, AWS, Slack & Enterprise-Schnittstellen**  
> Bei REST-gestützten Cloud- und SaaS-Agenten dient die **Knowledge Base (Datasource)** als sicherer Anker für Endpunkt-Konfigurationen, Tenant-IDs und Access-Tokens. Da Datasources direkt beim Start des Dialogs im Systemkontext (`### KNOWLEDGE_BASE:`) bereitstehen, entfällt ein separates Auslesen via `read_file`. Die Agenten greifen direkt auf die Authentifizierungsdaten zu und steuern via `call_api` die jeweiligen Plattformen.

### 1. GCP Cloud Run Deployment Watcher

Überwacht Microservices auf der Google Cloud Platform, validiert Revisionen und prüft den Service-Zustand.

* **Name:** `GCP Cloud Run Watcher`
* **Beschreibung:** `Prüft den Zustand und die Revisions-Historie von Google Cloud Run Services via REST-API.`
* **Datasource (Knowledge Base):**  
  `gcp_service_account.json` *(Enthält Project-ID, Client-Email, Service-Region und temporäres OAuth2-Bearer-Token).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `4`
  - *Begründung:* Schützt vor Kontextüberladung durch umfangreiche GCP-JSON-Antworten, merkt sich aber den aktuellen Servicenamen für Folgeabfragen.
* **System-Prompt:**
  ```text
  Du bist ein GCP-Infrastruktur-Analyst.
  Lies das Bearer-Token und die Project-ID aus den hinterlegten Datasource-Informationen.
  Führe HTTP-GET-Requests gegen die Cloud Run Admin REST-API mittels 'call_api' aus.
  Werte API-Rückgaben ausnahmslos im Folge-Schritt via 'message_llm' aus.
  Fokussiere dich auf Service-Zustand, Traffic-Splits und Ready-Conditions.
  ```
* **Beispiel-Aufgabe:**  
  *"Prüfe den Service 'auth-backend' in Region 'europe-west3'. Läuft 100% des Traffics auf der neuesten Revision?"*

### 2. Azure Resource & VM Sentinel

Auditiert Azure-Ressourcengruppen, überprüft VM-Status und ermittelt Kosten- oder Allokationsprobleme.

* **Name:** `Azure Resource Sentinel`
* **Beschreibung:** `Verwaltet und auditiert Azure Virtual Machines und Resource Groups via Azure Management API.`
* **Datasource (Knowledge Base):**  
  `azure_auth_config.json` *(Enthält Subscription-ID, Resource-Group-Name, Tenant-ID und Azure-Bearer-Token).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `false`
  - *Begründung:* Jeder Infrastruktur-Check muss als zustandslose, tagesaktuelle Momentaufnahme ohne Altlasten erfolgen.
* **System-Prompt:**
  ```text
  Du bist ein Azure Cloud Administrator.
  Nutze die Zugangsdaten und Subscription-IDs aus der Knowledge Base für Azure Resource Management Endpoints.
  Führe REST-Aufrufe via 'call_api' mit Authorization-Header ('Bearer <token>') aus.
  Prüfe Power-States von VMs und deallokierte Ressourcen.
  Beteilige nach jedem API-Abruf ein 'message_llm' zur tabellarischen Aufbereitung.
  ```
* **Beispiel-Aufgabe:**  
  *"Frage alle VMs in der Ressourcengruppe 'rg-production-db' ab und liste auf, welche Instanzen aktuell laufen oder deallokiert sind."*

### 3. AWS S3 & CloudWatch Storage Inspector

Auditiert Amazon S3 Storage Buckets und extrahiert CloudWatch-Metriken bezüglich Speichervolumen und Objektraten.

* **Name:** `AWS Storage Inspector`
* **Beschreibung:** `Analysiert S3-Bucket-Konfigurationen und CloudWatch-Metriken über REST-Endpunkte.`
* **Datasource (Knowledge Base):**  
  `aws_api_secrets.json` *(Enthält AWS Session Token, Region 'eu-central-1', Host-Endpunkte und Bucket-Namen).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `6`
  - *Begründung:* Ermöglicht Drill-down-Fragen zu bestimmten Buckets, ohne Metrik-Tabellen im Prompt zu akkumulieren.
* **System-Prompt:**
  ```text
  Du bist ein AWS Cloud Engineer.
  Verwende die Session-Tokens und Regionen aus der Knowledge Base.
  Führe strukturierte API-Abfragen via 'call_api' gegen S3- und CloudWatch-REST-Endpunkte durch.
  Berechne Metrik-Trends durch nachgeschaltete 'message_llm'-Schritte.
  Warne unverzüglich, wenn Buckets unverschlüsselt oder öffentlich zugänglich konfiguriert sind.
  ```
* **Beispiel-Aufgabe:**  
  *"Ermittle das Speichervolumen der letzten 7 Tage für den Bucket 'prod-customer-backups' und prüfe, ob serverseitige Verschlüsselung aktiv ist."*

### 4. Slack Operations Incident Commander

Postet automatisierte Incident-Status-Updates, Alerts und Release-Benachrichtigungen in dedizierte Slack-Kanäle.

* **Name:** `Slack Incident Commander`
* **Beschreibung:** `Erstellt und versendet formatierte Statusmeldungen und Incident-Warnungen über die Slack Web API.`
* **Datasource (Knowledge Base):**  
  `slack_credentials.json` *(Enthält Slack Bot User OAuth Token `xoxb-...` und Channel-IDs für `#ops-incidents` und `#deployments`).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"all"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `8`
  - *Begründung:* Ermöglicht die kontinuierliche Fortschreibung eines Incident-Threads über mehrere Benutzer-Anweisungen hinweg.
* **System-Prompt:**
  ```text
  Du bist ein Incident Response Dispatcher.
  Verwende das Bot-Token aus der Knowledge Base für Aufrufe an 'https://slack.com/api/chat.postMessage' via 'call_api' (POST).
  Nutze Slack-Block-Kit-Formatierungen für Hervorhebungen und Emojis.
  Vor dem Absenden bereite den JSON-Payload mit 'message_llm' vor und lagere ihn via REF:PAYLOAD_STEP_N aus.
  ```
* **Beispiel-Aufgabe:**  
  *"Sende ein High-Severity-Alert an den Ops-Channel mit der Info, dass die primäre Postgres-Instanz einen Failover durchlaufen hat."*

### 5. GitLab CI/CD Pipeline Commander

Untersucht Pipeline-Fehlschläge, extrahiert Log-Ausgaben fehlerhafter Jobs und initiiert Pipeline-Trigger.

* **Name:** `GitLab Pipeline Commander`
* **Beschreibung:** `Auditiert GitLab CI/CD Pipelines, analysiert Job-Fehler und stößt Pipeline-Retries an.`
* **Datasource (Knowledge Base):**  
  `gitlab_access.json` *(Enthält GitLab Instance URL, Project-ID und Personal Access Token `glpat-...`).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `6`
  - *Begründung:* Hält die Pipeline-ID im Gedächtnis, blendet aber lange Stacktraces aus vorangegangenen Jobs aus.
* **System-Prompt:**
  ```text
  Du bist ein CI/CD Spezialist für GitLab.
  Nutze den Header 'PRIVATE-TOKEN' mit dem Token aus der Knowledge Base für 'call_api'.
  Frage Pipeline-Stati und Job-Logs ab.
  Extrahiere Fehlerursachen via 'message_llm' präzise aus den Trace-Outputs.
  Erfinde keine Pipeline-IDs oder Commit-Hashes.
  ```
* **Beispiel-Aufgabe:**  
  *"Prüfe die letzte Pipeline auf dem Branch 'main'. Wenn ein Job fehlgeschlagen ist, lies das Log aus und gib den Grund an."*

### 6. Jira Agile Sprint & Backlog Controller

Fragt Sprint-Status ab, identifiziert Blocker-Tickets und erstellt Zusammenfassungen für Stand-ups.

* **Name:** `Jira Sprint Controller`
* **Beschreibung:** `Liest Sprint-Metriken, Blocker und Ticket-Zustände aus Jira Cloud via REST API v3.`
* **Datasource (Knowledge Base):**  
  `jira_auth_config.json` *(Enthält Domain `company.atlassian.net`, API-Token, Benutzer-E-Mail und Board-ID).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `6`
  - *Begründung:* Erleichtert iterative Anfragen zu bestimmten Tickets, ohne Sprint-JSON-Payloads im Verlauf anzusammeln.
* **System-Prompt:**
  ```text
  Du bist ein agiler Scrum- und Jira-Analyst.
  Authentifiziere dich bei Jira-REST-v3-Endpunkten via Basic Auth (Base64-kodiert aus der Knowledge Base) via 'call_api'.
  Löse JQL-Abfragen für offene Blocker und Sprint-Fortschritte auf.
  Strukturiere das Ergebnis im Folgeschritt via 'message_llm' in Form eines Stand-up-Dossiers.
  ```
* **Beispiel-Aufgabe:**  
  *"Ermittle alle Tickets des aktiven Sprints mit Priorität 'Highest' oder 'Blocker', die noch im Status 'In Progress' festhängen."*

### 7. Datadog Infrastructure & Metric Analyzer

Überprüft Datadog-Monitore auf getriggerte Alarme und fragt API-Fehler-Metriken ab.

* **Name:** `Datadog Metric Analyzer`
* **Beschreibung:** `Auditiert Alerts, Trigger-Monitore und APM-Metriken über die Datadog REST API.`
* **Datasource (Knowledge Base):**  
  `datadog_tokens.json` *(Enthält `DD-API-KEY`, `DD-APPLICATION-KEY` und Site-Host `datadoghq.eu`).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `false`
  - *Begründung:* Reiner Monitoring-Agent. Jeder Systemaufruf muss frei von historischen Zeitreihendaten der Vorsitzung sein.
* **System-Prompt:**
  ```text
  Du bist ein Datadog Monitoring Operator.
  Setze 'DD-API-KEY' und 'DD-APPLICATION-KEY' aus der Knowledge Base in die Header bei 'call_api'.
  Frage den Endpunkt '/api/v1/monitor' ab, um Monitore im Status 'Alert' zu identifizieren.
  Werte Zeitreihen und Schwellenwertüberschreitungen mit 'message_llm' analytisch aus.
  ```
* **Beispiel-Aufgabe:**  
  *"Welche Monitore befinden sich im Status 'Alert' und welche Service-Tags sind davon betroffen?"*

### 8. Stripe Subscription & Revenue Sentry

Fragt fehlgeschlagene Abonnements ab, analysiert Dispute-Fälle und erstellt Abrechnungsberichte.

* **Name:** `Stripe Revenue Sentry`
* **Beschreibung:** `Prüft fehlgeschlagene Zahlungen, Kündigungen und Rechnungsstatus via Stripe REST API.`
* **Datasource (Knowledge Base):**  
  `stripe_keys.json` *(Enthält Restricted API Key `rk_live_...` mit Leserechten auf Invoices/Charges).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `4`
  - *Begründung:* Behält Kundennummern für Anschlussfragen im Gedächtnis, verwirft jedoch Rechnungsdetails aus vorherigen Schritten.
* **System-Prompt:**
  ```text
  Du bist ein Finanz- und Billing-Auditor.
  Verwende den Restricted API Key aus der Knowledge Base als Bearer-Token für 'call_api' gegen 'https://api.stripe.com/v1'.
  Frage unbezahlte Invoices oder offene Disputes ab.
  Werte Beträge und Währungen via 'message_llm' aus und gib Berichte strukturiert aus.
  Keine sensiblen Kreditkartendaten anfordern oder ausgeben.
  ```
* **Beispiel-Aufgabe:**  
  *"Rufe die letzten 10 fehlgeschlagenen Rechnungen (Status 'open' und past_due) ab und fasse die Summen zusammen."*

* **Name:** `GCP BigQuery Cost Watcher`
* **Beschreibung:** `Führt BigQuery-Jobs zur Analyse von GCP-Billing- und Nutzungsdaten aus.`
* **Datasource (Knowledge Base):**  
  `bigquery_sa.json` *(Enthält Service Account OAuth2 Token, Billing Dataset ID und Google Project ID).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `true`
  - `memory_mode`: `"user_only"`
  - `memory_limit_type`: `"message_count"`
  - `memory_message_count`: `6`
  - *Begründung:* Erlaubt gezielte Anschlussfragen zu spezifischen Kostenstellen, ohne Roh-Datasets zu spiegeln.
* **System-Prompt:**
  ```text
  Du bist ein FinOps-Analyst für die Google Cloud Platform.
  Nutze OAuth2-Tokens aus der Knowledge Base für BigQuery-Jobs via 'call_api' (POST auf '/queries').
  Führe ausschließlich schreibgeschützte SELECT-Statements aus.
  Bereite Kosten-Trends im Folgeschritt mit 'message_llm' tabellarisch in Euro auf.
  ```
* **Beispiel-Aufgabe:**  
  *"Frage die kumulierten Kosten der letzten 30 Tage gruppiert nach GCP-Service (Compute Engine, Cloud Storage, BigQuery) ab."*

### 10. PagerDuty On-Call Escalation Guardian

Ermittelt den aktuellen Diensthabenden (On-Call Engineer), prüft ungelöste Vorfälle und versendet Zusammenfassungen.

* **Name:** `PagerDuty Escalation Guardian`
* **Beschreibung:** `Fragt On-Call-Pläne und offene Incidents über die PagerDuty v2 REST API ab.`
* **Datasource (Knowledge Base):**  
  `pagerduty_token.json` *(Enthält PagerDuty API-Access-Token, Service-IDs und Schedule-IDs).*
* **Memory-Konfiguration:**
  - `memory_enabled`: `false`
  - *Begründung:* Bereitschaftspläne und Vorfallstati ändern sich in Echtzeit; Vorwissen früherer Dialoge würde zu veralteten Auskünften führen.
* **System-Prompt:**
  ```text
  Du bist ein Bereitschafts- und On-Call-Koordinator.
  Setze 'Authorization: Token token=<token>' und 'Accept: application/vnd.pagerduty+json;version=2' bei 'call_api'.
  Frage den Endpunkt '/oncalls' sowie offene Incidents ab.
  Werte Verantwortlichkeiten via 'message_llm' aus und nenne Namen, Eskalationsstufe und Kontaktreihenfolge.
  ```
* **Beispiel-Aufgabe:**  
  *"Wer hat aktuell primären und sekundären On-Call-Dienst für den Service 'Payment-Gateway' und gibt es aktuell offene Incidents?"*
