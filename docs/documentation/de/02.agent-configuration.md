## 1. Anatomie eines Trinity-Agenten

Ein Agent in Trinity besteht aus vier Säulen:

```
┌────────────────────────────────────────────────────────────────────────┐
│                             TRINITY AGENT                              │
├───────────────────────┬───────────────────────┬────────────────────────┤
│ 1. Identität & Prompt │ 2. Memory & Kontext   │ 3. Knowledge Base      │
│   • Name              │   • memory_enabled    │   • Angehängte Dateien │
│   • Description       │   • memory_mode       │   • Inline-Inhalte     │
│   • System Prompt     │   • memory_limit_type │   • Workspace-Dateien  │
│                       │   • message_count     │                        │
├───────────────────────┴───────────────────────┴────────────────────────┤
│ 4. Tool Execution Runtime                                              │
│   • Task Chain Planner (JSON Task Engine)                              │
│   • Lokale Werkzeuge (Filesystem, Web, ODF, E-Mail, APIs)              │
│   • Delegationsschnittstelle (Sub-Agent-Calls)                         │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Konfigurationsparameter & Datenmodell

Die Domain-Entität `Agent` im Flask-Backend (`app/domain/models/agent.py`) definiert alle Attribute:

| Parameter | Datentyp | Standard | Beschreibung |
| :--- | :--- | :--- | :--- |
| `name` | `string` | *(Pflicht)* | Eindeutige, prägnante Bezeichnung (1 bis 100 Zeichen). |
| `description` | `string` | `None` | Kurzbeschreibung des Einsatzgebiets (max. 500 Zeichen). |
| `system_prompt` | `string` | `None` | Benutzerdefinierte Instruktion für Rolle, Tonalität und Tool-Verhalten. |
| `memory_enabled` | `boolean` | `false` | Aktiviert oder deaktiviert das Konversationsgedächtnis vollständig. |
| `memory_mode` | `enum` | `"user_only"` | Filtert den Verlauf: `"user_only"` (nur Nutzer-Prompts) oder `"all"` (inkl. Assistenten-Antworten). |
| `memory_limit_type` | `enum` | `"all"` | Art der Begrenzung: `"all"` (unbegrenzt) oder `"message_count"` (letzte $N$ Nachrichten). |
| `memory_message_count`| `integer` | `None` | Begrenzung bei `"message_count"`. Muss $> 0$ sein, wenn aktiv. |
| `datasources` | `list` | `[]` | Liste verknüpfter Knowledge-Base-Dokumente (`Datasource`). |

## 3. Kontextsteuerung & Agent Memory

Trinity nutzt ein mehrstufiges Speichersystem. Das LLM erhält bei jeder Anfrage eine strukturierte Sicht auf die bisherige Historie.

### Speicher-Topologien im Vergleich

```
Modus: "user_only"                             Modus: "all"
┌────────────────────────┐                    ┌────────────────────────┐
│ User: Wie erstelle ... │                    │ User: Wie erstelle ... │
├────────────────────────┤                    ├────────────────────────┤
│ [Assistant übersprungen]                     │ Assistant: Hier ist ...│
├────────────────────────┤                    ├────────────────────────┤
│ User: Ergänze Schritt 2│                    │ User: Ergänze Schritt 2│
└────────────────────────┘                    └────────────────────────┘
-> Spart ~50-70% Tokens                       -> Vollständiger Dialogkontext
-> Ideal für Task-orientierte Agenten         -> Ideal für Coaching, Rollenspiele
```

### Wahl der passenden Strategie

1. **Reine Task- und Schnittstellen-Agenten (Web-Scraping, Git-Bots, Code-Generatoren):**
   - `memory_enabled`: `true`
   - `memory_mode`: `"user_only"`
   - `memory_limit_type`: `"message_count"`
   - `memory_message_count`: `6` bis `10`
   - *Vorteil:* Minimiert Token-Kosten und verhindert, dass umfangreiche Code-Rückgaben alter Schritte das Kontextfenster blockieren.

2. **Reflektierende & iterative Agenten (Lektorat, Dokumentenerstellung, Support):**
   - `memory_enabled`: `true`
   - `memory_mode`: `"all"`
   - `memory_limit_type`: `"message_count"`
   - `memory_message_count`: `14` bis `20`
   - *Vorteil:* Der Agent erinnert sich an seine eigenen Zwischenentwürfe und Formulierungsvorschläge.

3. **Stateless Pipelines (Microservice-Worker):**
   - `memory_enabled`: `false`
   - *Vorteil:* Jede Anfrage ist vollständig isoliert. Keine Drift durch vorherige Gespräche.

## 4. Prompt-Architektur & System-Prompt-Design

### Der zweistufige Aufbau (Base Prompt vs. Custom Prompt)

Trinity setzt vor jeden benutzerspezifischen Systemprompt automatisch den systemweiten Basis-Prompt (`base_agent.prompt.md`). Dieser verankert unveränderliche Kernregeln:
- Definition der verfügbaren Werkzeuge und deren Schemata
- Verzeichnisstruktur und Pfade der aktuellen Session
- JSON-Formatregeln für Task Chains
- Auslagerung von Nutzlasten via Content-Payloads (`REF:PAYLOAD_STEP_N`)

Der individuelle `system_prompt` des Agenten ergänzt diesen Basis-Prompt um Rolle, Fachwissen und Handlungsanweisungen.

### Aufbau eines produktiven System-Prompts

Ein robuster System-Prompt sollte in vier Abschnitte unterteilt sein:

1. **Rolle & Mission:** Wer ist der Agent? Was ist sein primärer Mehrwert?
2. **Arbeitsweise & Heuristiken:** Welche Schritte unternimmt er standardmäßig? Wann greift er auf welche Werkzeuge zu?
3. **Formatierungs- & Ausgabevorgaben:** Wie strukturiert er Zwischenschritte und Endergebnisse?
4. **Grenzen & Negativ-Beispiele:** Was darf der Agent explizit *nicht* tun?

### Werkzeug-Konditionierung & Task-Chain-Steuerung

Um Fehlplanungen der internen Task-Engine zu vermeiden, sollte der System-Prompt konkrete Verhaltensmuster für Werkzeuge vorgeben:

- **Einstufige vs. Mehrstufige Pläne:** Bei unbekannten Ziel-Links muss der Agent erst einen 1-Phasen-Abruf planen (`is_complete: false`), um Links zu sichten, bevor er Detailseiten lädt.
- **Keine Blind-URLs:** Der Agent darf keine URLs erfinden. Suchen müssen über `web_search` eingeleitet werden.
- **Payload-Nutzung:** Quellcode, Templates und lange Markdown-Texte müssen zwingend über den Content-Payload-Block ausgelagert werden, um fehlerhafte JSON-Escapes zu verhindern.
- **ODF-Dokumente:** Bei `.ods`-Tabellen muss explizit auf englische Formelnamen hingewiesen werden (`=SUM()`, `=AVERAGE()`).

## 5. Arbeiten mit Knowledge Bases & Datasources

Dokumente, die über den API-Endpunkt `/api/v1/agents/<agent_id>/datasources` hochgeladen werden, landen in der Knowledge Base des Agenten:

- Dokumentinhalte werden beim Start des Chats in den Systemkontext unter dem Marker `### KNOWLEDGE_BASE:` eingebettet.
- **Wichtig für den System-Prompt:** Dem Agenten sollte mitgeteilt werden, dass Knowledge-Base-Inhalte bereits im Prompt vorliegen und dafür **kein** `read_file` ausgeführt werden darf. Das Werkzeug `read_file` dient ausschließlich für Dateien, die während der Session im Konversationsordner erzeugt wurden.

## 6. Sub-Agent-Orchestrierung

Trinity erlaubt es Agenten, Aufgaben an Kollegen weiterzureichen. 

```
┌─────────────────────────┐
│     Leit-Agent          │
│ (z.B. IT-Projektleiter) │
└────────────┬────────────┘
             │  tool: "message_agent"
             │  target_agent_id: "6d08b3a3-..."
             ▼
┌─────────────────────────┐
│     Sub-Agent           │
│ (Frontend-Architekt)    │
└─────────────────────────┘
```

**Regeln für Multi-Agenten-Prompts:**
- Verweise auf Sub-Agenten müssen die exakte UUID aus der Konfigurationsliste nutzen.
- Das Ergebnis eines Sub-Agenten ist final (`is_complete: true`). Es bedarf keiner nachgelagerten Neu-Evaluation durch ein weiteres `message_llm`, es sei denn, mehrere Berichte werden zusammengeführt.
- Zirkelbezüge werden von Trinity bei einer Verschachtelungstiefe von $3$ abgefangen.

## 7. Vollständige Referenzkonfigurationen

### Szenario A: Research Assistant & Fact Checker

Ein Agent zur fundierten Internet-Recherche, der Quellen prüft, Querverweise zieht und strukturierte Dossiers anlegt.

#### Konfigurations-Payload (REST-API)
```json
{
  "name": "Fact Finder & Analyst",
  "description": "Führt strukturierte Web-Recherchen durch und erstellt quellenbasierte Dossiers.",
  "memory_enabled": true,
  "memory_mode": "user_only",
  "memory_limit_type": "message_count",
  "memory_message_count": 8,
  "system_prompt": "Du bist ein präziser Fact-Checking- und Research-Analyst.\n\n### ARBEITSWEISE:\n1. Führe bei Informationsbedarf zuerst eine gezielte Suche mittels 'web_search' durch.\n2. Wähle die relevantesten 2-3 Quell-URLs aus und lese den Volltext über separate 'fetch_url'-Schritte aus (keine Zusammenfassungen aus Teasern!).\n3. Verarbeite die extrahierten Texte via 'message_llm' zu einem kohärenten Dossier.\n4. Speichere das Ergebnis strukturiert via 'write_file' als Markdown-Datei unter 'reports/analysereport.md'.\n\n### REGELN:\n- Keine erfundenen Fakten oder URLs.\n- Nenne zu jeder Kernaussage die Primärquelle mit Datum.\n- Halte Antworten sachlich, neutral und tabellarisch gegliedert."
}
```

### Szenario B: Autonomous DevOps & Git Release Bot

Ein Agent zur Erstellung von Release Notes und Changelogs auf Basis von Git-Patches und Commits.

#### Konfigurations-Payload (REST-API)
```json
{
  "name": "Git Release Manager",
  "description": "Erstellt strukturierte CHANGELOGs und Release Notes aus Patches und Diffs.",
  "memory_enabled": true,
  "memory_mode": "user_only",
  "memory_limit_type": "message_count",
  "memory_message_count": 4,
  "system_prompt": "Du bist ein hochpräziser Release- und Changelog-Manager für Softwareprojekte.\n\n### FORMATVORGABEN:\nBefülle Changelogs strikt nach folgendem Standard:\n\n# [Unreleased]\n\n### Added\n- Feature 1\n- Feature 2\n\n### Changed\n- Änderung 1\n\n### Fixed\n- Bugfix 1\n\n### REGELN:\n- Verwende ausschließlich britisches oder amerikanisches Englisch.\n- Nutze '-' als Aufzählungszeichen.\n- Trenne den ersten Punkt jeder Kategorie mit einer Leerzeile von der Überschrift.\n- Quellcode-Ausschnitte in Backticks setzen.\n- Dateien stets über 'write_file' im Arbeitsbereich sichern."
}
```

### Szenario C: Office Document Generator (ODF & Reporting)

Ein Agent, der Geschäftsberichte analysiert und formatierte LibreOffice-Dokumente (`.odt`, `.ods`) generiert.

#### Konfigurations-Payload (REST-API)
```json
{
  "name": "Business Reporting Specialist",
  "description": "Erstellt automatisierte OpenDocument-Dateien (.odt/.ods) für Geschäftsberichte.",
  "memory_enabled": true,
  "memory_mode": "all",
  "memory_limit_type": "message_count",
  "memory_message_count": 12,
  "system_prompt": "Du bist Spezialist für automatisierte Büroberichte und ODF-Dokumente.\n\n### DOKUMENTENVERARBEITUNG:\n1. Verwende 'manage_odf' mit 'action: create' für neue Dokumente.\n2. Wähle 'doc_type: ods' für Tabellen und 'odt' für Textdokumente.\n3. FORMELN IN TABELLEN: Verwende AUSSCHLIESSLICH englische Funktionsnamen (z. B. '=SUM(B2:B10)', '=AVERAGE(C2:C10)'), niemals deutsche Bezeichnungen wie '=SUMME'!\n4. Wenn Zahlen aus vorherigen Schritten extrahiert werden, schalte stets einen 'message_llm'-Schritt vor, der reine Textdaten ohne Markdown liefert.\n\n### TONALITÄT:\nProfessionell, geschäftsmäßig und präzise."
}
```

## 8. Checkliste vor dem Deployment

Bevor ein Agent produktiv geschaltet wird, sollten folgende Punkte geprüft werden:

- [ ] **Name & Beschreibung:** Sind Rolle und Aufgabengebiet klar abgegrenzt?
- [ ] **Token-Ökonomie:** Ist `memory_mode: "user_only"` aktiv, falls der Agent primär Code oder lange Dateien generiert?
- [ ] **Task-Chain-Tauglichkeit:** Verlangt der Prompt bei Datenverarbeitung explizit nach Zwischenschritten via `message_llm`?
- [ ] **Werkzeug-Disziplin:** Wurde dem Agenten untersagt, URLs oder Fakten zu halluzinieren?
- [ ] **Formel-Kompatibilität:** Sind ODF-Formeln auf englische Bezeichnungen konditioniert?
- [ ] **Knowledge Base:** Sind alle benötigten Referenzdokumente angehängt und überflüssige Altlasten entfernt?
